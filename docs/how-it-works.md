# How Qwen3.8 27B works with TensorFold

## How the model works

Consider the prompt “Mira put the blue mug on the shelf. The mug is”. The model must choose the next **token**, a piece of text from its vocabulary. A token can represent a whole word, part of one, a space combined with a word, or punctuation. The tokenizer converts the prompt into integer IDs. At each position the model looks up its ID in an **embedding** table and receives 5,120 learned numbers. The table, and the matrices that transform those numbers, are the model’s **weights**. These remain fixed while the server answers. The vector at each position, and the memories the layers create as they read the story, are **state**. State belongs to this prompt and changes after each new token. [Qwen model overview](https://huggingface.co/Qwen/Qwen3.8-27B#model-overview) · [Pinned target configuration](https://huggingface.co/Vontra/Qwen3.8-27B-MLX-4bit/blob/22d8d538154e0e5b6f8dcb1fcc74a60a0798104c/config.json)

The vector at the final position starts as a representation of “is” and ends up carrying information about the mug and the earlier sentence. A learned output matrix, the **language-model head**, gives each vocabulary row a score called a *logit*. A calculation called softmax turns the eligible scores into probabilities that sum to one. As a toy example, “ blue” might receive 0.45, “ on” 0.30 and all other candidates 0.25 combined. Greedy decoding picks the highest score. Sampling draws from the allowed candidates, so two continuations can differ. If the first token is “ on”, the server appends it and asks a new question of the model with that longer prefix. A sequence of these next-token decisions produces an answer. [Qwen model card](https://huggingface.co/Qwen/Qwen3.8-27B) · [Pinned model dimensions](https://huggingface.co/Vontra/Qwen3.8-27B-MLX-4bit/blob/22d8d538154e0e5b6f8dcb1fcc74a60a0798104c/config.json)

### Follow “is” through 64 layers

```text
prompt IDs -> embedding per position (5,120 numbers)
            -> repeat 16 times, with different weights in every layer
               [Gated DeltaNet + dense feed-forward] × 3
               [Gated Attention + dense feed-forward] × 1
            -> final normalization -> 248,320 vocabulary scores -> one ID
```

Each layer does two jobs. A **token mixer** lets information from earlier positions alter the current one. Then a **feed-forward network** transforms features at this position. Each sublayer has a residual connection that adds the newly computed update to its incoming vector. RMS normalization puts the features on a controlled numerical scale before the transformation. A useful earlier feature, such as information about the color, can thus continue through layers while another transformation adds evidence about location. There are 16 groups, yielding 48 recurrent token mixers and 16 full-attention mixers. All 64 have a dense feed-forward network. [Qwen model overview](https://huggingface.co/Qwen/Qwen3.8-27B#model-overview) · [Qwen-family reference implementation](https://github.com/huggingface/transformers/blob/main/src/transformers/models/qwen3_5/modeling_qwen3_5.py)

**Gated DeltaNet remembers associations in a fixed amount of space.** A learned projection of the current vector produces a query, key and value. Think of a key as an address described by features, the value as what should be associated with it, and the query as the features a position wants to retrieve. A learned short convolution can mix inputs from the current and three previous positions. The layer keeps a matrix for each value head and updates it in text order. It decays past state, reads the value the matrix currently associates with this key, and writes a fraction of the difference between that prediction and the new value. “Delta” names that corrective difference. A learned gate controls its strength. The layer reads the updated matrix with the query, gates the result and projects it back to the model width. [Gated DeltaNet paper](https://arxiv.org/abs/2412.06464) · [Reference recurrence](https://github.com/huggingface/transformers/blob/main/src/transformers/models/qwen3_5/modeling_qwen3_5.py)

Suppose later text says that Mira moved the mug to a drawer. A learned association can shift toward the new location without allocating another row in a permanent list of every mention. The real model uses continuous vectors for such updates. There are 16 sets of query/key features and 48 sets of value features, each 128 numbers wide. Multiple value heads can share addressing features while representing different information. A fixed-size matrix is economical during long conversations. Summarizing many positions into it makes exact recovery of every detail difficult. [Checkpoint head counts and convolution width](https://huggingface.co/Vontra/Qwen3.8-27B-MLX-4bit/blob/22d8d538154e0e5b6f8dcb1fcc74a60a0798104c/config.json) · [Gated DeltaNet paper](https://arxiv.org/abs/2412.06464)

**Every fourth layer can look directly at earlier positions.** In full gated attention, each preceding token supplies a key and a value. The query for “is” scores those keys, including ones associated with both mentions of “mug”. The scores become weights and the layer computes a weighted sum of the values. A gate derived from the current input modulates the retrieved features before the output projection. A causal mask prevents any position in the prompt from using future text. This model has 24 query heads and four shared key/value heads, or six query heads per KV head. Each head has width 256. A rotary position embedding rotates 64 coordinates of the query and key according to position so the match can depend on distance as well as content. The server can save keys and values in a **KV cache** and read them again on the next step. [Qwen model overview](https://huggingface.co/Qwen/Qwen3.8-27B#model-overview) · [Attention implementation](https://github.com/huggingface/transformers/blob/main/src/transformers/models/qwen3_5/modeling_qwen3_5.py)

**What “27B dense” means for an individual token.** The language model has about 27 billion parameters. Every token in a layer runs through the same feed-forward weights in that layer. Two projections expand its normalized 5,120 features into two sets of 17,408 features. A smooth activation called SiLU transforms one set so it can gate the other by elementwise multiplication. The down projection maps the result back to 5,120 numbers for the residual update. The computation can express combinations of detected features, for example how a noun’s description interacts with its role in a sentence. Flash Next is a different Qwen model with routed experts, sparse selection of attention blocks and an extra n-gram table. The 27B checkpoint’s dense feed-forward and periodic full-attention paths are the ones being timed here. [Pinned dimensions](https://huggingface.co/Vontra/Qwen3.8-27B-MLX-4bit/blob/22d8d538154e0e5b6f8dcb1fcc74a60a0798104c/config.json) · [Qwen dense implementation](https://github.com/huggingface/transformers/blob/main/src/transformers/models/qwen3_5/modeling_qwen3_5.py) · [Flash Next overview](https://huggingface.co/Qwen/Qwen3.8-Flash-Next#model-overview)

**How pixels can join the sentence.** Images and sampled video frames go through a 27-layer visual encoder. It receives patch features from 16-by-16-pixel regions, uses 1,152-wide hidden vectors and 16 attention heads, and groups two time slices per temporal patch. A spatial merger combines 2-by-2 patch groups and produces 5,120-wide features. The processor places these at visual positions alongside text, so “what color is the mug?” can refer to information carried by the image. Image resolution and frame count therefore affect prompt length and prefill work. The language model still predicts text through its vocabulary head, whose 248,320 padded rows have weights separate from the input embedding table. Qwen also trained a one-layer multi-token prediction (MTP) module over multiple future steps. The serving profile below selects a separately trained draft checkpoint. [Pinned text and vision configuration](https://huggingface.co/Vontra/Qwen3.8-27B-MLX-4bit/blob/22d8d538154e0e5b6f8dcb1fcc74a60a0798104c/config.json) · [Qwen’s image and video examples](https://huggingface.co/Qwen/Qwen3.8-27B)

## How this recipe runs it on one DGX Spark

### Loading the checkpoint into the CUDA engine

The target is Vontra’s MLX 4-bit conversion at `22d8d538154e0e5b6f8dcb1fcc74a60a0798104c`. “MLX” identifies how this checkpoint was packed. TensorFold’s CUDA engine reads that layout and performs the model computations on the Spark’s NVIDIA GB10. The 4-bit *affine* format stores compact integer codes with a scale and offset shared by each group of 64 weights. Sixteen possible codes can therefore represent different ranges in different groups. The engine can repack weights at load time for its GPU matrix kernels. This saves weight storage and memory traffic. Rounding to those levels can change the logits relative to the original higher-precision model. [Vontra checkpoint](https://huggingface.co/Vontra/Qwen3.8-27B-MLX-4bit/blob/22d8d538154e0e5b6f8dcb1fcc74a60a0798104c/README.md) · [TensorFold v0.6.0 CUDA kernels](https://github.com/ashhart/TensorFold/blob/v0.6.0/src/tensorfold/families/qwen3_5/cuda/README.md)

`serve.sh download` pulls the digest-pinned ARM64 TensorFold v0.6.0 image plus the target and z-lab DFlash2 drafter. The draft revision is `50307d4c4cde6860d4eee73e2547cd786fe8e8a4`. It records an offline reference for each snapshot because the engine resolves these models by repository ID. The weights and draft need about 20 GB of disk plus the container and runtime cache. `start` checks the references and configuration files, mounts the Hugging Face cache read-only and provides a writable `/cache` for runtime data. The server listens on `127.0.0.1:8888` with the model name `Qwen3.8-27B`. The measured container log reported drafts enabled. [Launcher](../serve.sh) · [Install and runtime details](../README.md#runtime)

### Prefill builds two different kinds of memory

A `/v1/chat/completions` request first passes through the message template and tokenizer. **Prefill** moves those prompt positions through the model and saves the state needed to continue from the last one. The 48 GDN layers save their recurrent matrices and short convolution histories. The 16 full-attention layers save per-token keys and values. TensorFold’s patched engine stores the main KV rows in FP8 E4M3, which uses one byte per element. The prefill option also allows eight-bit activations during prompt calculations. Activations are temporary computed values. These precision choices affect different data from the packed four-bit weights, and both can influence output. The launcher enables vision with limits of 50 images and 16,384 image/video tokens in the respective settings. The measured runs in this repository used text. [Launch profile](../serve.sh) · [Pinned FP8 cache and prefill implementation notes](https://github.com/MiaAI-Lab/Qwen3.8-27B-DGX-Spark-TensorFold/blob/c11ff138871cf43d12898d79dbfa4dc952d17ca4/README.md)

One prompt token’s KV payload is 16 attention layers × 4 KV heads × 256 dimensions × 2 for key and value × 1 byte, or **32 KiB**. A full 262,144-token sequence needs **8 GiB** for that payload before recurrent states, transient wider copies and other buffers. An eight-slot server with a 32 GiB shared KV pool can accommodate many combinations of short requests. Eight simultaneous full windows would need 64 GiB for KV data alone. The actual memory is shared by CPU and GPU, including the OS and other processes. The launcher defaults to an 8 GiB reserve. The measured profile used `TENSORFOLD_MEMORY_RESERVE_GIB=0` in an isolated run. The zero value allows the admission calculation to spend more of the existing physical memory. [Pinned capacity calculation](https://github.com/MiaAI-Lab/Qwen3.8-27B-DGX-Spark-TensorFold/blob/c11ff138871cf43d12898d79dbfa4dc952d17ca4/README.md) · [Local profile and measurements](../README.md#runtime)

### DFlash2 suggests several continuations and the target decides

During **decode**, each accepted token updates the sequence and state. Running all 64 target layers separately for every token can require many passes over resident weights. DFlash2 takes features from target layer IDs 5, 19, 33, 47 and 61. It feeds those features and a block with masked future positions to a five-layer draft network. The pinned configuration has block size eight, a 2,048-position sliding attention window and a two-tap convolution that can exchange information between neighboring draft positions. The draft network estimates multiple candidates per position in one pass. Its selector retains up to 16 candidates per position and uses rank-256 features to assess transitions between neighbors. For example, “top shelf” and “side table” may each be plausible. Scoring transitions lets the drafter account for whether “shelf” follows “top” or “side”. [DFlash2 model card](https://huggingface.co/z-lab/Qwen3.8-27B-DFlash2/blob/50307d4c4cde6860d4eee73e2547cd786fe8e8a4/README.md) · [Pinned DFlash2 configuration](https://huggingface.co/z-lab/Qwen3.8-27B-DFlash2/blob/50307d4c4cde6860d4eee73e2547cd786fe8e8a4/config.json) · [Authors’ description](https://inco.ai/blog/dflash2/)

TensorFold uses those scores to build a small **tree** of candidate continuations. A branch contains earlier choices that later positions on that branch can see. In a verification pass, the full target computes scores for candidate positions while respecting each branch’s history. From the current prefix the engine follows children that match the target’s choices, emits the target’s next selection when the path ends, and commits only the state on the accepted path. Discarded alternatives therefore cannot change the next query’s KV or recurrent memory. TensorFold’s CUDA implementation uses the same per-row calculations for serial and tree verification and keys sampling draws by position. Its reference is serial execution on this engine with the same precision and sampling setup. The pinned upstream recipe reports greedy and sampled parity checks. This repository’s local sweep records speed and retrieval results, with no independent parity or draft acceptance-rate measurement. [TensorFold tree policy](https://github.com/ashhart/TensorFold/blob/v0.6.0/src/tensorfold/families/qwen3_5/cuda/draft_tree.py) · [Verifier and state commit](https://github.com/ashhart/TensorFold/blob/v0.6.0/src/tensorfold/families/qwen3_5/cuda/multi.py) · [Upstream parity checks](https://github.com/MiaAI-Lab/Qwen3.8-27B-DGX-Spark-TensorFold/blob/c11ff138871cf43d12898d79dbfa4dc952d17ca4/README.md)

With `--parallel 8`, the scheduler can combine verification work for independent clients on the one device. As a request completes, its capacity can serve another. Each request retains its own generated IDs, current GDN state and attention history. Prefix reuse can resume a matching saved prompt state. The engine’s compiled CUDA and Triton kernels implement the matrix work and candidate verification. The local launcher specifies no graph capture sizes and the benchmark collected no graph-replay counts. A wall-clock rate therefore measures the combined effects of the scheduler, kernels, cache, drafter and client. [TensorFold v0.6.0 scheduling implementation](https://github.com/ashhart/TensorFold/blob/v0.6.0/src/tensorfold/families/qwen3_5/cuda/README.md) · [Local launcher](../serve.sh)

### Reading a generation rate and a prompt rate

The November 20 decode sweep issued short hash-map explanation requests directly to TensorFold, with the other Flash Next server paused. Thinking was enabled. Temperature 0.7 scales the scores, top-k 20 restricts the candidate set to twenty and top-p 1 leaves their full probability mass available. Each stream produced 400 tokens. For one through five concurrent streams the best aggregate waves across three repetitions reached **43.8, 79.9, 105.4, 121.5 and 140.2 tokens/s**. The single stream’s time to first token (TTFT) was 98 ms. At five streams the median user waited 496 ms for a first token and then saw 29.8 tokens/s. Aggregate decode spans the earliest first to the latest last streamed token and excludes each stream’s first token from the count. Thinking tokens can start that clock before visible answer text appears. [Benchmark client](../benchmark.py) · [Decode and prefill receipts](../results/benchmark-2026-11-20.json)

The two cold-prefill tests used separate calibration requests to estimate prompt length because this engine exposed no tokenizer endpoint. The final runs reported zero cached prompt tokens and thinking was off. At 32,568 input tokens the first token arrived after 18.72 seconds, or **1,740 input tokens/s**. At 199,061 it arrived after 206.78 seconds, or **963 input tokens/s**. Both responses reproduced the inserted key exactly. These rates divide actual prompt tokens by client TTFT and capture the wait before generation. The monitor sampled a 49,567 MiB peak GPU footprint during the separate long-prefill phase. The eight-slot setting, five-short-stream sweep and one-long-request measurements describe three different capacity questions.
